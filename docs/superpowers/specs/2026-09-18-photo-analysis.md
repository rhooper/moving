# Photo analysis in the background — design and API contract

2026-09-18. Requested: *"after adding a photo, begin llm categorization in
background. keep results with photos. auto-add suggested items, keep only
unique items (merge). dynamically show contents list as edited. update autogen
contents summary when llm vision completes. add estimated runtimes for photo
recognition so that the spinner is a bit of a countdown circle."* Plus: *"allow
tapping on an autogenerated label to edit its text."*

## A rule is being reversed, on purpose

Until now a vision draft was a **proposal**: shown in a review panel, never
applied (`ai.py`, CLAUDE.md "Never auto-apply a draft"). The user has asked for
the opposite for photos: analyse without being asked, and add what is found.
What survives of the old rule is the part that protected people's own work:

- Items the model adds are tagged `source='ai'` and shown as *autogenerated*.
- A person's item is never renamed, re-counted or removed by the model.
- A summary a person typed is never overwritten — only one that is empty or was
  itself autogenerated (`boxes.summary_source = 'auto'`).
- Renaming an autogenerated item makes it the person's: `source` becomes
  `'manual'` and the model leaves it alone from then on.

## Behaviour

1. Uploading a photo to a record that holds contents (box, tub — not a loose
   item) queues one analysis job for that photo. A re-upload that dedupes to an
   existing photo queues nothing new.
2. One worker thread runs jobs oldest-first, one at a time (the model is the
   bottleneck; parallel calls only make each slower). Jobs live in `ai_jobs`,
   so a deploy mid-analysis loses nothing: on startup, `running` jobs go back
   to `pending`.
3. When a job finishes, its result is stored on the job row (which carries the
   `photo_id`), then applied:
   - **Merge:** each suggested item is matched against the record's existing
     items by normalised name (case, surrounding space, trailing plural `s`/`es`).
     No match → added with `source='ai'`. Match on an `ai` item → quantity
     raised to the larger of the two. Match on a `manual` item → untouched.
   - **Summary:** if `summary_source='auto'` or the summary is empty, it is
     rebuilt from the merged item list (`summarise.from_items`) and marked
     `auto`. A `PATCH` that sets `content_summary` marks it `manual`.
4. **Estimates:** the expected duration of a job is the median `duration_ms` of
   the last 10 successful photo jobs for the same model, or 20 000 ms when there
   is no history. A queued photo's wait includes the jobs ahead of it.

## API contract

```
GET /api/boxes/{code}/photos
  each photo gains:
  "analysis": null | {
      "status":       "pending" | "running" | "done" | "error",
      "remaining_ms": int,        # best estimate until done, from now; 0 when done/error
      "total_ms":     int,        # whole expected span of the job, so the ring's
                                  #   fraction complete = 1 - remaining_ms / total_ms
      "items_found":  int | null, # done: how many items the model saw in this photo
      "error":        str | null
  }

POST /photos/{photo_id}/analyse           -> 202, the photo (with "analysis")
  Queue (or re-queue) analysis of one photo. Retry after an error, or re-run.

PATCH /api/items/{item_id}  {"name"?: str, "qty"?: int}   -> 200, the item
  Renaming an item whose source is "ai" sets its source to "manual".
  404 unknown item; 422 empty name.
```

Events on `/api/events` (no `origin`, since no device caused them):

- `photos.changed` (code) — every job state change: queued, started, finished, failed.
- `items.changed` (code) — a finished job added or re-counted items.
- `box.updated` (code) — a finished job rewrote the autogenerated summary.

## For UI work without a model

`MOVING_VISION_PROVIDER=stub` selects a canned provider: it sleeps
`MOVING_VISION_STUB_SECONDS` (default 3) and returns a fixed draft (`kettle`,
`3 mugs`, `toaster`). Deterministic, offline, and fast enough for a browser check.

## Frontend

- The "Draft contents" button and review panel go away; analysis is automatic.
  Each photo shows its state: a countdown ring while pending/running, *"N items
  found"* when done, the error and a Retry when it failed.
- The ring is a countdown from `remaining_ms`, animated client-side. Past zero
  and not yet done, it becomes an indeterminate spinner rather than sitting full
  and lying about being finished.
- `items.changed`, `photos.changed` and `box.updated` for the open record update
  the items list, the photo strip and the (pristine) summary **in place**, even
  while a full refresh is being held because a field is focused. A dirty or
  focused summary field is never touched.
- Tapping an item's name turns it into an inline field; Enter or blur saves via
  `PATCH /api/items/{id}`, Escape cancels.
